# Agent Arena · 产品深度设计（v2 方向）

> 这是一份功能设计文档，不是视觉稿。目标：把"多模型辩论表演"改造成"能拿去下决策的压力测试台"。
> 判断依据：代码实读（`apps/arena/*`、`static/app.js`、`templates/index.html`）+ 19 场历史战报（`runs/*/transcript.json`）。

---

## 0. 一句话结论

**当前产品只在"观赏"这一层成立，在"决策"这一层是空的。**

README 说这个产品用于"从分歧中发现被忽略的风险、证据和假设"、"比较不同模型在同一问题上的真实表现"。这两句话在代码里都没有对应实现：

- **分歧被扔掉了。** 19 场战报里最常见的一句话是"方案同质化、增量最少"。模型在第 2 轮就收敛成同一套话（细分/轻资产/先收钱/止损），之后每一轮淘汰的都是"不够有新意"的人。而"最有价值的主张 + 它被谁反驳了 + 它活到了第几轮"这套数据完全没有被采集。赛制奖励"不重复"，但产品的价值承诺是"保留分歧"——**这是产品内最大的自相矛盾**。
- **模型没法被比较。** 投票是单维的（投最站不住的 / 投最该留下的），产出只有一个"胜者"。没有跨场可比的量化指标，所以"哪个模型更强"这个问题，当前版本答不了。README 承诺的"比较不同模型"是空的。

**改法**：把产出从"胜者"改成三件套 —— **裁决 + 分歧台账 + 模型画像**；把赛制从"群体淘汰"改成"带评分的压力测试"。下面的所有改动都从这一句推导。

---

## 1. 定位重定义

| | 现在 | 改后 |
|---|---|---|
| 一句话 | 让多个大模型坐上一张辩论桌 | 让一个决策在多个模型面前被反复撞击，直到你能签字 |
| 用户角色 | 观众 | 决策者 |
| 一场赛的产出 | 一个胜者 + 一段热闹的过程 | 裁决（含失效条件）+ 分歧台账 + 模型画像 |
| 核心动作 | 看着模型吵 | 读结论、查风险、对比模型 |
| 成功标准 | 看得爽 | 敢照着做、知道哪里可能错 |

**为什么必须换定位**：现有赛制是"群体淘汰产生唯一胜者"，这个赛制结构天然回答不了"哪个模型更强"（对照组被逐轮消灭，只剩一个幸存者，无法比较）。要回答"谁更强"，必须先有**多维评分**产生可比的数字；要回答"这个决策哪里可能错"，必须先有**主张台账**记录每个原子主张的存亡。两件事都要改赛制才能拿到数据。

---

## 2. 机制层改动（最核心，7 项）

### 改动 1 · 同一轮发言并行执行 —— 当前最大的浪费

**问题**：`moderator.py` 的 `Arena.run()` 里，发言是**串行 for 循环**。6 人 6 轮 = 36 次串行 API 调用。实测 `runs/20261101-202159` 那场耗时 **1430 秒（24 分钟）**，而这些模型单次发言平均只要 10–40 秒。时间全花在互相等待上。

**为什么并行是安全的**：赛制的可见性约束是"第 N 轮的模型看不到第 N 轮别人的输出"。代码里 `prior_speeches = _prior_speeches_for(active, rounds)` 在发言循环**之前**一次性算好（只含第 1..N-1 轮），各模型的 prompt 里本来就只有跨轮内容。**并行执行不破坏任何赛制约束**，这是纯工程收益。

**改法**：
- `moderator.py::Arena.run()`：把发言 for 循环换成 `ThreadPoolExecutor`（并发度 = min(人数, 4)，避免同时打爆服务商）。
- 流式输出的处理：每模型的 chunk 各自缓冲到 `RoundRecord` 里，**不立即 emit**；本轮全部完成后，按 `record.order` 顺序把缓冲的流"重放"给前端（`model_output` 事件照旧发，只是提前算好、按序发）。
- 新增一个配置 `speech_mode`：`parallel_buffered`（默认，快）/ `sequential_live`（保留现有实时观感）。用户可在登记页切换。

**代价与取舍**：并行模式下"实时"变成"本轮并行生成中 → 完成后按序播放"。这是真的取舍，我不假装没有。但如果 24 分钟 → 5 分钟，用户不会在乎少了一点"实时感"，而会在乎少等 19 分钟。**默认走并行，实时模式保留给想看现场的人。**

**预期收益**：单场时长 1430s → 约 400s（3.5×）。这是所有改动里投入产出比最高的。

### 改动 2 · 点评范围收窄 + 引入"自我修正台账"

**问题**：三个叠加的病。

1. `prompts.py::build_speech_prompt` 注入的是"前几轮**完整**发言"（所有轮次所有人），轮次越多 prompt 越长，模型注意力被稀释；
2. 任务要求"选出此前**所有**参赛者里最好的和最差的" —— 等于每轮重评全局，模型只能给套话。战报里清一色是"整体务实""共识清晰""方案同质化"，**没有一句具体批评**；
3. 模型**没有修正通道**：它上一轮说了什么、被谁批评了什么，下一轮完全看不见，所以它永远在提新角度而不是迭代观点。退化是结构决定的，不是模型笨。

**改法**：
- **注入范围**：只给**上一轮**所有人的发言（每人截断 400 字）+ 我自己的论点台账 + 针对我的具体批评。
- **任务改写**：从"选出全场最好/最差"改为**"必须点名回应一条针对你的具体批评，并明确说明你接受还是反驳"**。一句都不回应就视为无效发言。
- **新增论点台账**：`moderator.py` 内维护 `self._ledger: dict[str, list[LedgerEntry]]`，每个 `LedgerEntry` = `{round, stance, claim, accepted_critiques, rejected_critiques}`。
  - `claim`（一句话核心论点）：让模型在发言末尾多输出一行 `【主张】<一句话，可被投票的原子命题>`。既然已经要求结构化输出，加这一行的边际成本几乎为零，但把"抽主张"这件难事从后处理交给了模型自己。
  - `accepted/rejected_critiques`：从上一轮点评和投票理由里，机械地抓取**点名提到该模型**的那些句子（模型名出现在理由文本里即可命中）。
- **新增两个 prompt 参数**：`build_speech_prompt(..., last_round_only=True, my_ledger=[...], critiques_of_me=[...])`。
- **解析**：新增 `parse_claims(text)`、`extract_critiques_for(name, round_speeches, votes)`，都放 `moderator.py` 顶部的工具函数区，和现有 `extract_view` / `extract_stance` 并列。

**预期收益**：点评从套话变成具体交锋；模型会自我修正（"知微上一轮说承保，这一轮改成…"）；**主张台账有了数据源**（见改动 6）。

### 改动 3 · 投票从单维改成多维评分

**问题**：`prompts.py::build_vote_prompt` 只要求输出 `{"vote": "...", "reason": "..."}`。单维、无强度、无分数。而且 `moderator.py::parse_vote` 里 `reason` 被 `[:40]` **硬截断**——理由是"为自己的判断负责"的核心证据，40 字砍掉的恰恰是最有价值的部分（战报里所有理由都是半句话）。

**改法**：
- **输出 schema 升级**：
  ```json
  {
    "scores": {"模型A": {"论证": 8, "证据": 5, "可执行": 7, "增量": 9}, "模型B": {...}},
    "vote": "模型B",
    "reason": "<不限长，说明为什么这一票这样投，以及对最强对手的具体异议>"
  }
  ```
  四个维度对应现有投票标准里的四条（推进命题 / 论据成立 / 是否空泛 / 是否有增量），只是从定性变成定量。
- **理由不截断**，改为存 200 字上限 + 保留完整文本在战报。
- **淘汰规则**：仍按 `vote` 决定谁出局（保持赛制可读性），但**分数矩阵作为独立数据落库**，用于跨场比较模型强弱。
- **兼容**：`parse_ballot()` 先试新 schema，失败再回退旧的 `parse_vote()`，老战报不受影响。

**预期收益**：这是"比较不同模型在同一问题上的真实表现"这句话第一次有了数据支撑。档案页的模型画像由此而来。

---

### 改动 4 · 评审席降权，且票权分布必须可见

**问题**（严重）：`moderator.py` 里 `voters = list(self._judges) + list(active)` —— **评审与存活者同权**。看 `runs/20261101-202159` 第 6 轮：6 张票里 **4 张来自评审**（hy3、小智、小码、灵溪都已出局），最终胜者实际上是被一批**已经被淘汰的模型**选出来的。第 4 轮更极端："随机移出投票人 hy3 后决出"。

这在方法论上是错的：被淘汰的模型可能有强烈动机投票给"看起来最像对的"（延续自己的对立面），且票权随轮次膨胀，最终结果越来越由早期出局者决定。README 说"淘汰者转为评审"是亮点，**这个机制要保留，但权重必须修**。

**改法**：
- 评审票 **权重 0.5**（可在 `ArenaConfig` 配），存活者票权重 1.0。
- **硬约束**：当存活者只剩 2 人时，评审票权重总和**不得超过存活者票权重总和**。防止"后排意见绑架前排"。
- 计票改为加权：`counts[target] += weight`。
- 战报和 UI 必须显示**每轮的票权分布**：`存活者票 xN（权重 1.0）· 评审票 yN（权重 0.5）`。
- UI 上评审射线用更细的线宽/更低透明度区分（配合已有"评审"标签）。

### 改动 5 · 平局裁决去掉随机性

**问题**：`moderator.py::_resolve_vote` 的平局处理会 `removed = random.choice(remaining_voters)` —— **随机移除一位投票人**，投票结果直接决定淘汰谁。战报原话："淘汰：小码 3 票（2 人平票；随机移出投票人 hy3 后决出）"。这意味着同一场辩论重跑一次可能换一个胜者，结论不可复现、不可解释。

**改法**：三级确定性裁决，**彻底删除 `random.choice`**：
1. 多维评分矩阵的分数差（改动 3 引入）—— 高分者留；
2. 若分数差为 0：存活者票优先于评审票；
3. 若仍相同：按本轮**新增主张数**（不是字数长度）—— 主张多者留。

`mock.py` 里的 `random` 只用于假数据，保留。

**预期收益**：结果可复现。这是"能拿去下决策"的前提——一个不能复现的结论没法用。

---

### 改动 6 · 主张台账（Claim Ledger）—— 本产品最有价值的差异化资产

**问题**：这个产品叫"辩论"，但**辩论的产物是分歧，而分歧现在一个字节都没被保存**。战报只有"谁说了什么"和"谁投了谁"，没有"哪些具体主张被提出过、被谁挑战过、最后哪条活下来了"。

**改法**：
- 每次发言解析出 **1–3 条原子主张**（来源：改动 2 引入的 `【主张】` 行；缺失时用 `extract_view` 的首句兜底）。
- 台账记录：`{claim_id, text, author, round, stance, challengers: [names], supporters: [names], final_status}`。
- 后续轮次里，某模型引用了某条主张（做文本包含匹配）或反驳了它 → 更新 `challengers` / `supporters`。
- 最终裁决里**被写入的主张** → `final_status = 'adopted'`；被明确否定的 → `'rejected'`；无人再提 → `'dormant'`。
- 战报新增一节"主张演化"，同时输出到 `transcript.json` 的 `claims` 字段。

**产出物**：
- 战报 Markdown 里加"主张存活表"：`| # | 主张 | 提出者 | 提出轮 | 被谁挑战 | 结局 |`
- 前端记录页新增"主张台账"视图。

**为什么这是核心竞争力**：竞品（LangGraph、AutoGen、各家的多智能体框架）全都停在"让多个 agent 聊起来"。**没有人在做"把讨论里产生的判断提取成可追溯的资产"**。这件事做好了，Agent Arena 就不再是一个 demo，而是决策基础设施。

---

### 改动 7 · 收敛检测与动态轮数（用已经在手但被浪费的数据）

**问题**：`extract_stance()` 已经解析了每个模型的 `【立场】-100..100`，前端也渲染了立场场（`stanceField`），但**后端从没用过 stance 做任何决策**。它是纯装饰。

**改法**：
- 每轮结束后计算存活者 stance 的**极差**（max - min）。
- **收敛判定**：极差 ≤ 25（都站到同一边去了）→ 不再淘汰，触发"收敛收束"环节：每人做一次"最后的补充或明确保留异议"，然后直接进最终裁决。这一步能把这类"第 3 轮就开始复读"的辩论提前 2 轮结束（当前 `runs/20261101-202159` 那场 6 轮里后 3 轮基本在复读）。
- **分歧过大**：极差 ≥ 150 且轮次未用完 → 轮次预算 +1（`max_rounds` 从静态变动态）。
- stance 数据顺带作为**观点聚类的依据**：立场相近 + 主张文本相近 → 在台账里归为同一簇，UI 上立场场可以直接按簇着色。

**预期收益**：省掉无信息量的后段轮次（直接省 API 费用和时间），同时让"轮次"变成有意义的变量而不是固定 N-1。

## 3. 产出层改动（结论、战报、档案）

### 改动 8 · 最终结论升级为"整合式裁决"

**问题**：`prompts.py::build_final_prompt` 让胜者基于 `_digest(rounds)`（4000 字截断）写最终结论。**被淘汰模型的好观点被直接丢弃**。战报第 5 轮星澜那句"可挽回毛利×兑现概率 > 打扰与履约成本"，比最后胜者的结论更值得保留，但没人记录它去哪了。

**改法**：最终 prompt 增加输入 `eliminated_claims`（从台账提取的、来自已淘汰模型的高分主张），并强制输出结构：
```
【结论】<一句话，明确立场>
【论据】<=3 条，每条标注来源模型
【保留的分歧】<至少 1 条仍未解决的分歧，标注是谁提的>
【失效条件】<在什么情况下这个结论不成立>
```
"保留的分歧"和"失效条件"是整个产品最该有、现在完全缺失的两段话——**决策者最需要知道的就是哪里可能错**。

### 改动 9 · 战报结构升级（transcript.json v2）

新增字段（v1 老战报继续可读，读时按缺字段降级）：
```
rounds[].scores        : 多维评分矩阵
rounds[].weight_breakdown : {alive_votes, judge_votes, judge_weight}
rounds[].stance_spread : number
rounds[].round_claims  : 本轮新产生的主张
claims                 : 全局主张台账
budget                 : {calls, tokens_estimate, wall_clock, per_model}
schema_version         : 2
```
Markdown 战报（`report.py`）同步加"主张存活表"和"票权分布"两节。

### 改动 10 · 档案页从"表"升级为"对比台"

**问题**：`api.py::history` 只返回元数据列表，档案页是一张 17 行的表。**同一命题跑过多场时，用户只能一场场点开**。而"比较不同模型"这个核心场景恰恰需要横向对比。

**改法**：
- **按命题聚合**：同一命题的多场折叠成一组，显示"跑了 3 场，胜者分别是 星澜/星澜/知微"。
- **对比视图**：选 2–3 场 → 并排看胜者、评分矩阵、主张演化、最终结论。
- **模型画像**（新增，依赖改动 3 的分数矩阵）：每个模型在全部历史里的画像 —— 平均总分、平均被点名批评次数、作为评审时的胜率、平均登场轮次、胜率。
- **成本列**：每场时长 + 估算花费。
- **导出**：单场 / 多场导出 Markdown，接大哥的知识库（`library` skill）。

## 4. 可控性与工程层改动

### 改动 11 · 成本可见 + 预算上限

**问题**：6 人一场跑 24 分钟，**全程不知道花了多少钱**。`providers.py::_read_stream` 读流时把 `usage` 字段直接丢掉了（很多服务商在 `stream_options.include_usage` 时会返回）。没有预算上限 = 一次手滑就能烧掉一整天的额度。

**改法**：
- `providers.py::_read_stream` / `_invoke`：捕获 `usage`（`prompt_tokens` / `completion_tokens`），透传到 `CallResult`，累加进 `ArenaResult.budget`。
- `schemas.py::StartRun` 增加：`max_calls`、`max_wall_clock_seconds`、`max_tokens_per_call`、`budget_cny`（可选，硬上限）。
- `moderator.py`：每次调用前检查预算，超限则优雅收束（和"收敛收束"同一个出口），并在战报里标注"因预算收束"。
- UI：会场页 HUD 加"已用 N 次调用 / 预算剩余"。

### 改动 12 · 可中止 + 状态一致性修复

**问题**：
1. `services.py::Manager` **没有 cancel**。跑到一半想停，只能杀进程。
2. 进程被杀后，DB 里那场 run **永远停在 `status='running'`**（`database.py` 只在 worker 正常/异常结束时写终态）。重启后 `api.py::active_run` 会把它当成"进行中"接回来，档案页显示"中断"但状态是 running —— 数据不一致。

**改法**：
- `Manager.cancel(run_id)`：置取消标志，`moderator.py` 在每轮边界和每次调用后检查，优雅结束并归档（`status='cancelled'`，保留已完成轮次）。
- 服务启动时（`config/server.py`）：把 DB 里 `status='running'` 的陈旧记录刷成 `status='interrupted'`。
- 前端会场页加"停止比赛"按钮，档案页状态点新增"已中止"。

### 改动 13 · 命题结构化 + 背景材料

**问题**：命题是一个 `max_length=2000` 的字符串。模型在真空里空谈——战报里所有发言都在讲通用商业逻辑，没有一条涉及用户自己的业务上下文。这正是"决策压力测试"最缺的东西。

**改法**：
- `schemas.py::StartRun` 的 `proposition: str` → 保留，但新增 `context` 对象：
  ```json
  { "question": "...", "background": "...", "constraints": ["..."], "criteria": ["..."], "files": ["..."] }
  ```
- `prompts.py`：分段注入，`criteria` 直接对应投票维度（改动 3 的四个评分维度应由用户 criteria 覆盖默认值 —— 这才是"评据"该有的用法）。
- `files`：本地文本/PDF（走 `workbuddy-pdf` skill 抽文本）作为共同背景，存 `runs/<id>/context/`。
- UI：登记页的命题区从单个 textarea 改成三段折叠：`命题 / 背景与约束 / 评判标准`。

### 改动 14 · 辩论人格预设（谨慎引入，且不影响投票）

**问题**：所有模型被要求做同一件事（综合发言 + 提新观点），角色同质化是必然结果。战报里第 3 轮之后所有模型都在说同一套"轻资产/先收钱"。

**改法**：模型配置新增可选 `persona` 预设 —— `审计员`（专挑证据漏洞）/ `务实派`（只看落地成本）/ `反方`（强制唱反调）/ `红队`（攻击最强论点）/ `归纳者`（只做分歧归纳不表态）。
- **默认不给**，用户显式分配。
- **严格边界**：人格只作用于**发言环节**；**投票环节人格一律关闭**。否则就是角色扮演式作弊，票就不可信了。
- 战报里标注每个模型被分配的人格 —— 否则读战报的人无法判断发言的立场是被强制的还是模型自己的。

### 改动 15 · 前端拆分（不引入构建链）

**问题**：`static/app.js` 2366 行单文件 Vue 应用 + `static/style.css` 2960 行单文件。再加"对比视图 / 主张台账 / 成本面板 / 命题三段式"，这个文件会失控。

**改法**（保持"无前端构建链"这条项目约束）：
- JS 拆成 `static/js/{shared,register,venue,record,archive,models}.js`，用普通 `<script>` 顺序引入 + 全局 `app.component(...)` 注册，不引入打包器。
- CSS 拆成 `static/css/{base,venue,record,archive,models}.css`。
- 事件契约（`handleEvent` 的 switch）**保持 case 名称不变**，新增事件追加在末尾。

### 改动 16 · 赛制参数化（为后续多赛制打底）

`moderator.py::ArenaConfig` 目前只有 `vote_mode` / `max_rounds` / `timeout` / `retries`。把赛制差异（发言方式、投票方式、是否淘汰、轮次策略）收敛成配置项，提示词按赛制选不同模板集（`prompts.py` 按赛制拆成 `prompts/eliminate/`、`prompts/support/`）。这样以后加"瑞士轮""打分制""辩论赛（正反两队）"是加配置，不是改主流程。

| 3 | 投票多维评分 + 理由不截断（3） | 赛制 | 高 | 中 | **Now** |

**依赖关系**：

## 6. 指标体系

**北极星指标**：**每场产生的"被采纳的可执行主张"数量**
—— 不是场次、不是时长、不是观感。是"这场辩论最终留下了几条能拿去做的判断"。

| 类型 | 指标 | 目标（改动全部落地后） |
|---|---|---|
| 北极星 | 每场被采纳主张数 | ≥ 6 |
| 驱动 | 主张存活到最终的比例 | ≥ 40% |
| 驱动 | 投票理由非空率（不再截断） | ≥ 95% |
| 驱动 | 每场至少 2 条来自不同作者的保留分歧 | 100% |
| 驱动 | 评分矩阵完整率 | ≥ 90% |
| 健康 | 单场时长（中位） | ≤ 8 分钟 |
| 健康 | 单场 API 调用数 | ≤ 2.5 × 人数 × 轮数 |
| 健康 | 技术性失败率 | ≤ 3% |
| 健康 | 评审票占总票权比例 | ≤ 40% |
| 健康 | 同输入重跑结果一致率 | 100%（去掉随机裁决后必须达到） |
| 健康 | 收敛提前收束的场次占比 | ≥ 25% |

**健康指标里最该盯的两个**：评审票权占比（防止前排被后排绑架）和重跑一致率（防止结论不可复现）。这两个不达标，前面所有价值都塌。

## 7. Non-goals（明确不做，防止范围蔓延）

- ❌ 不做账号体系、多用户、云同步 —— 保持"本地优先、单人使用"的产品边界
- ❌ 不做模型微调、训练、权重相关的一切
- ❌ 不做实况观赛/弹幕/直播间 —— 观赏性扩张会让工程复杂度爆炸，而我们要的是决策价值
- ❌ 不做通用工作流编排器（不要长成 n8n）
- ❌ 不做移动端原生 App（现有响应式够用）
- ❌ 不做"多 agent 协作框架"（AutoGen/LangGraph 的地盘）—— 我们做的是**辩论结果的资产化**，不是编排
- ❌ 不做自动化的"客观答案判定" —— 命题没有标准答案，机器不能替代人的判断

---

## 8. 落地顺序建议

1. **先修可信度，再谈智能。** 改动 2/4/5 属于"把现在已有的结果变得可信"，成本低、收益直接。所有功能设计之前先做这个。
2. **并行发言是白捡的性能。** 单独拎出来做，做完立刻能感觉到。
3. **主张台账单独占一个迭代。** 它同时改提示词、数据结构、战报、前端四处，是本设计里最大的一块。
4. **档案对比台是"让别人看见价值"的地方。** 用户不会自己跑 19 场然后手动对比 —— 这个页面做出来，产品的说服力才成立。
5. **命题结构化是最后一块拼图。** 它让"决策压力测试"名副其实，也是让大哥自己用得下去的关键。
